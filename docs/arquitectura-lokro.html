Frontend

Cómo se construyó

Un solo proyecto que hace de frontend y de backend al mismo tiempo

Next.js App Router — monolito moderno

No hay un servidor separado. Next.js unifica el frontend (lo que ve el usuario) y el backend (APIs, autenticación, lógica de negocio) en un solo proyecto. Vercel lo despliega automáticamente con cada push.

Estructura de rutas — 4 zonas

Next.js permite agrupar rutas entre paréntesis para separar lógica sin afectar la URL. Cada zona tiene su propio layout, middleware y restricciones de acceso.

(marketing)

Landing, registro, login, términos, privacidad. Sin autenticación. Accesible por cualquiera.

(user)

Mapa, solicitudes, pago, chat, tracking GPS. Requiere rol USER.

(provider)

Dashboard, agenda, ingresos, perfil. Requiere rol PROVIDER.

(admin)

Panel de gestión. Requiere rol ADMIN. Solo el equipo accede.

Server Components vs. Client Components

⚙️ Server Components

Corren en el servidor — cargan datos de la BD directamente y envían el HTML listo al navegador. Más rápido, más seguro: las claves API nunca llegan al cliente.

🖥️ Client Components

Corren en el navegador — usados para el mapa interactivo, el chat en tiempo real, el seguimiento GPS y las notificaciones en vivo.

Servicios

Qué servicios usamos y para qué

Cada servicio resuelve un problema concreto del producto

Base de datos + Auth + Tiempo real
Supabase

Es la columna vertebral del proyecto. Un solo servicio que nos da base de datos, autenticación, WebSockets y almacenamiento de archivos.

PostgreSQL + PostGIS

12 tablas con relaciones. Las coordenadas GPS del prestador se guardan como tipo POINT geográfico, lo que permite hacer consultas de proximidad del tipo "mostrar prestadores a menos de 5 km".

Auth (JWT + Google OAuth)

Maneja login con email/contraseña y con Google. El token de sesión se guarda en una cookie HttpOnly — inaccesible para el JavaScript del navegador.

Realtime — WebSockets

Mantiene una conexión WebSocket permanente entre el servidor y el navegador. Cualquier cambio en la base de datos (nuevo mensaje, nueva notificación, posición GPS) llega al instante sin que el usuario recargue.

Row Level Security (RLS)

Políticas en la base de datos que bloquean accesos cruzados — un usuario no puede leer los datos de otro aunque haya un bug en el código de la aplicación.

Trigger automático — calificaciones

Cada vez que llega una reseña nueva, un trigger de PostgreSQL recalcula el promedio de calificación del prestador. No hay lógica manual en el código de la app.

Trigger automático — creación de perfil

Al registrarse, el trigger on_auth_user_created crea automáticamente la fila en users. Si es prestador, también crea su provider_profile vacío.

Seguridad

Lo que implementé — y por qué importa

Auditoría completa del código: cada vulnerabilidad identificada, corregida y documentada

Principio: fail-closed

Cuando algo falla o no está configurado, el sistema bloquea por defecto. En ningún caso se permite el acceso "provisional" o "en modo desarrollo". Si el secreto del webhook no está, se rechazan todas las peticiones. Si el JWT no es válido, se redirige a login. Nunca al revés.

4 capas de defensa independientes

Cada capa asume que la anterior puede estar comprometida o tener un bug. Si el middleware falla, RLS bloquea en la BD. Si RLS no cubre un caso, Zod rechaza el input. Si Zod pasa algo, el servidor valida de nuevo. Nunca una sola barrera.

① Middleware JWT → ② RLS en PostgreSQL → ③ Validación Zod → ④ Verificación en servidor
1
JWT en cookie HttpOnly — contra robo de sesión (XSS)

⚠ Sin esta medida: si un atacante logra inyectar JavaScript en la página (XSS), puede hacer document.cookie y robar el token de sesión. Con ese token puede operar como cualquier usuario sin conocer su contraseña.

✓ Con la medida: el flag HttpOnly hace que el navegador nunca exponga la cookie a JavaScript. document.cookie devuelve vacío. El token solo viaja en la cabecera HTTP — inaccesible para cualquier script.

2
Middleware + RLS — dos capas que no dependen la una de la otra

⚠ Sin esta medida: si el middleware tiene un bug o alguien accede directamente a la API, puede leer datos de cualquier usuario. Una sola capa de protección es un punto único de falla.

✓ Con la medida: el middleware verifica el JWT antes de cada página. Pero aunque ese código fallara, PostgreSQL aplica sus propias políticas RLS por usuario autenticado — directamente en la base de datos, sin pasar por el código de la app.

3
Escalada de privilegios bloqueada con Zod — nadie se hace ADMIN solo

⚠ Sin esta medida: la función setUserRole() tomaba el rol directamente del cuerpo de la petición. Un atacante podía enviar { role: "ADMIN" } desde las DevTools del navegador y darse acceso total al panel de administración.

✓ Con la medida: antes de tocar la BD, Zod valida con z.enum(['USER', 'PROVIDER']). Cualquier otro valor — incluyendo "ADMIN" — lanza un error y la función termina sin ejecutar nada.

4
Verificación de identidad en tracking GPS — acceso cruzado bloqueado

⚠ Sin esta medida: cualquier prestador autenticado podía ir a /tracking/[cualquier-id] y ver la ubicación GPS en tiempo real de un servicio que no era el suyo — incluyendo los datos del cliente.

✓ Con la medida: el servidor consulta qué prestador está asignado a esa solicitud y compara con el usuario autenticado: providerProfile.id === request.provider_id. Si no coincide, redirige inmediatamente sin mostrar nada.

5
HMAC-SHA256 en webhook de pagos — nadie puede fingir un pago aprobado

⚠ Sin esta medida: el endpoint /api/webhooks/mercadopago era público. Cualquiera podía hacer un POST con un payload falso que dijera status: "approved" y desbloquear un servicio sin pagar. El webhook original tenía if (!secret) return true — es decir, si la clave no estaba configurada, dejaba pasar todo.

✓ Con la medida: cada notificación llega firmada con HMAC-SHA256. El servidor recalcula la firma con la clave secreta compartida y la compara. Si no coinciden → 401. Si la clave no existe → 401 también (fail-closed). Solo Mercado Pago puede producir una firma válida.

6
Validación del monto en servidor — contra manipulación de precios

⚠ Sin esta medida: el monto viajaba desde el frontend al servidor sin verificación. Un atacante con DevTools podía interceptar la petición y cambiar el monto a $1 COP antes de que llegara, pagando un servicio a precio arbitrario.

✓ Con la medida: el servidor valida que el monto sea un número finito entre $100 y $100.000.000 COP. Cualquier valor fuera de ese rango — incluyendo negativos, Infinity o NaN — devuelve 400 y no crea la preferencia.

7
Validación de archivos por MIME type — contra upload de ejecutables

⚠ Sin esta medida: la validación original miraba solo la extensión del nombre del archivo. Un atacante podía renombrar script.exe a foto.jpg y subirlo al storage. Si ese archivo se servía sin restricción, podía ejecutarse en ciertos contextos.

✓ Con la medida: se verifica el Content-Type real del archivo — el tipo MIME que el navegador detecta del contenido binario, no del nombre. Solo pasan image/jpeg, image/png e image/webp. La extensión del archivo guardado también se deriva del MIME, no del nombre original.

8
Sanitización de búsquedas en el admin — contra inyección en PostgREST

⚠ Sin esta medida: el parámetro de búsqueda ?q= en el panel admin se pasaba directamente al filtro de PostgREST (la capa que convierte URLs en queries SQL). Un input como q=a),(b podía romper la estructura del filtro e inyectar condiciones no previstas en la consulta.

✓ Con la medida: antes de usar el parámetro se eliminan los caracteres especiales ( ) , % que tienen significado en la sintaxis de PostgREST, y se limita la longitud a 60 caracteres. Lo que llega al filtro es texto limpio.
