Frontend

Cómo se construyó

Un solo proyecto que hace de frontend y de backend al mismo tiempo

Next.js App Router — monolito moderno

No hay un servidor separado. Next.js unifica el frontend (lo que ve el usuario) y el backend (APIs, autenticación, lógica de negocio) en un solo proyecto. Vercel lo despliega automáticamente con cada push.

Estructura de rutas — 4 zonas

Next.js permite agrupar rutas entre paréntesis para separar lógica sin afectar la URL. Cada zona tiene su propio layout, middleware y restricciones de acceso.

(marketing)

Landing, registro, login, términos, privacidad. Sin autenticación. Accesible por cualquiera.

(user)

Mapa, solicitudes, pago, chat, tracking GPS. Requiere rol USER.

(provider)

Dashboard, agenda, ingresos, perfil. Requiere rol PROVIDER.

(admin)

Panel de gestión. Requiere rol ADMIN. Solo el equipo accede.

Server Components vs. Client Components

⚙️ Server Components

Corren en el servidor — cargan datos de la BD directamente y envían el HTML listo al navegador. Más rápido, más seguro: las claves API nunca llegan al cliente.

🖥️ Client Components

Corren en el navegador — usados para el mapa interactivo, el chat en tiempo real, el seguimiento GPS y las notificaciones en vivo.

Servicios

Qué servicios usamos y para qué

Cada servicio resuelve un problema concreto del producto

Base de datos + Auth + Tiempo real
Supabase

Es la columna vertebral del proyecto. Un solo servicio que nos da base de datos, autenticación, WebSockets y almacenamiento de archivos.

PostgreSQL + PostGIS

12 tablas con relaciones. Las coordenadas GPS del prestador se guardan como tipo POINT geográfico, lo que permite hacer consultas de proximidad del tipo "mostrar prestadores a menos de 5 km".

Auth (JWT + Google OAuth)

Maneja login con email/contraseña y con Google. El token de sesión se guarda en una cookie HttpOnly — inaccesible para el JavaScript del navegador.

Realtime — WebSockets

Mantiene una conexión WebSocket permanente entre el servidor y el navegador. Cualquier cambio en la base de datos (nuevo mensaje, nueva notificación, posición GPS) llega al instante sin que el usuario recargue.

Row Level Security (RLS)

Políticas en la base de datos que bloquean accesos cruzados — un usuario no puede leer los datos de otro aunque haya un bug en el código de la aplicación.

Todas con Row Level Security activado. Los datos de un usuario nunca son visibles para otro.

Trigger automático — calificaciones

Cada vez que llega una reseña nueva, un trigger de PostgreSQL recalcula el promedio de calificación del prestador. No hay lógica manual en el código de la app.

Trigger automático — creación de perfil

Al registrarse, el trigger on_auth_user_created crea automáticamente la fila en users. Si es prestador, también crea su provider_profile vacío.

Seguridad

Lo que implementé

Cada medida responde a un vector de ataque real que identificamos en la auditoría

Filosofía: fail-closed

Si algo falla o no está configurado, el sistema bloquea por defecto. Nunca permite el acceso "por si acaso" o "en modo desarrollo". Esto se aplica en todos los puntos de entrada críticos.

1
JWT en cookie HttpOnly — protección contra XSS

El token de sesión del usuario se guarda en una cookie con el flag HttpOnly. Esto significa que ningún JavaScript del navegador puede leerlo — ni el nuestro ni el de un atacante que inyecte código malicioso en la página. Es la defensa básica contra XSS que afecta autenticación.

2
Middleware + RLS — protección de rutas en dos capas

El middleware de Next.js verifica el JWT y el rol antes de cargar cualquier página. Si eso fallara, la base de datos tiene RLS activado — PostgreSQL bloquea el acceso a nivel de fila según el usuario autenticado. Un bug en el código de la app no puede exponer datos de otro usuario porque la BD tiene su propia política independiente.

3
Verificación de identidad en tracking GPS

Antes de mostrar la pantalla de seguimiento, verifico que el prestador autenticado sea el asignado a esa solicitud específica. Sin esta verificación, cualquier prestador registrado podría ver el seguimiento de servicios de otros. El código compara providerProfile.id === request.provider_id — si no coincide, redirige.

4
Validación de rol con Zod — no se puede escalar a ADMIN

La función que cambia roles de usuario acepta solo USER o PROVIDER. Aunque alguien manipule la petición y envíe role: "ADMIN", Zod rechaza el valor antes de que llegue a la base de datos. El esquema es explícito: z.enum(['USER', 'PROVIDER']).

5
HMAC-SHA256 en webhooks de Mercado Pago

El servidor de Mercado Pago firma cada notificación de pago con una clave secreta. Verifico esa firma antes de actualizar cualquier estado en la base de datos. Si el secreto no está configurado, el sistema rechaza todas las peticiones (fail-closed) — no permite pagos sin verificar. Sin esto, cualquiera podría fingir que un pago fue aprobado.

6
Validación del monto antes de crear el pago

El monto del pago se valida en el servidor: debe ser un número finito, mayor a $100 COP y menor a $100.000.000 COP. Sin este límite, un atacante podría manipular el valor desde el cliente e intentar crear preferencias de pago con montos absurdos o negativos.

7
Validación de archivos por MIME type real

Cuando un prestador sube fotos de perfil o portafolio, verifico el Content-Type real del archivo — no solo la extensión del nombre. Un archivo malware.jpg que en realidad es un ejecutable es rechazado. Solo se aceptan image/jpeg, image/png e image/webp.
