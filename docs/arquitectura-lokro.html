Protección de rutas — 2 capas

Middleware (Next.js)

Verifica el JWT y el rol antes de cargar cada página. Sin sesión → redirige a login.

RLS (PostgreSQL)

La base de datos aplica políticas de acceso por usuario, independiente del código.

Flujos

Cómo funciona por dentro

Los tres flujos más importantes del sistema

Flujo 1 — Registro

1
Email/contraseña o Google OAuth 2.0 Supabase Auth gestiona ambos. Con Google: redirige → obtiene token → intercambia por JWT en cookie HttpOnly.
2
Trigger PostgreSQL crea el perfil automáticamente on_auth_user_created inserta la fila en users. Si es prestador, también crea su provider_profile vacío.
3
Middleware redirige según el rol USER → /home · PROVIDER → /dashboard · ADMIN → /panel

Flujo 2 — Solicitud de servicio

Estados de la solicitud

PENDING → ACCEPTED → PAID → IN_PROGRESS → COMPLETED

1
Mapa con prestadores disponibles (Mapbox + PostGIS) Consulta provider_profiles donde available = true. Coordenadas como tipo POINT — permite queries de proximidad geográfica.
2
INSERT en service_requests → estado PENDING Server Action inserta la solicitud y notifica al prestador vía Supabase Realtime (WebSocket).
3
Prestador acepta → ACCEPTED · Tracking GPS en tiempo real El prestador transmite su posición a provider_locations. El usuario tiene una suscripción Realtime activa y ve el punto moverse en el mapa.

Seguridad

4 capas de protección

Cada capa asume que la anterior puede fallar

🚦

1 · Middleware

Valida JWT y rol antes de cada página. Sin sesión → login.

🔒

2 · RLS en PostgreSQL

La base de datos bloquea accesos cruzados aunque haya bugs en el código.

✅

3 · Validación con Zod

Todos los inputs se validan con esquemas estrictos antes de llegar a la BD.

🔐

4 · JWT en HttpOnly

La cookie de sesión no es legible por JavaScript. Protección contra XSS.

🔏

HMAC-SHA256 en webhooks

Firma criptográfica en cada notificación de pago. Sin firma válida → 401.

🛡️

service_role aislada

La clave de admin solo existe en el servidor. El cliente solo tiene la anon key.
